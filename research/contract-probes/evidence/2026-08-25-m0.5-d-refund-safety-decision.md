## B. Refund-Target Identifier Hard Gate

**U / unresolved.**

Current official Chapa documentation was reviewed on 2026-08-25:

- Refund documentation: <https://developer.chapa.co/refund>
  - documents `POST /v1/refund/<tx_ref>`;
  - describes `<tx_ref>` as a reference provided by Chapa after payment initiation;
  - uses a Chapa-style value in its request example;
  - separately says successful refund creation returns `data.ref_id` for refund verification.
- Verify Payments documentation: <https://developer.chapa.co/integrations/verify-payments>
  - documents `GET /v1/transaction/verify/<tx_ref>`;
  - explicitly describes `<tx_ref>` as the value set by the merchant during initialization.
- Accept Payments documentation: <https://developer.chapa.co/integrations/accept-payments>
  - distinguishes the merchant transaction reference from Chapa's internal `ref_id` in callback material.

Reasoning:

- The same `tx_ref` label is used for materially different descriptions.
- Provider materials also expose `reference`, `ref_id`, `payment_reference`, and `merchant_reference` in related transaction/refund contexts.
- The refund page does not unambiguously map its Chapa-provided path identifier to one named field obtainable from the reviewed D3 evidence.
- Inferring from the path placeholder or attempting candidates would violate the approved hard gate.

Decision: the refund mutation target identifier remains U. No identifier guessing, substitution, or trial refund is permitted.
