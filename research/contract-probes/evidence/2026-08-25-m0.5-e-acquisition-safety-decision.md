## 3. CLI authenticity classification

### Candidate A: `chapa webhook ping <url>` — REJECT

At pinned revision `d3f1a532181a11d4c42e8bd744b960c237d7ec2e`, `ping` constructs a static local object with `event = ping` and `message = Webhook test ping`, then calls `requests.post(url, json=data)` directly. It does not call a Chapa backend and attaches no provider-generated signature. It is local connectivity tooling, not provider evidence.

### Candidate B: `chapa webhook verifywebhook <url> --usekey ...` — REJECT

At the pinned revision, `verifywebhook` directly accesses the supplied target, locally constructs test data, locally computes the payload and secret-on-secret HMAC values from a caller-supplied key, and directly POSTs the result. It obtains no signature from a Chapa server. Further, it computes the payload candidate over `str(test_data)` while `requests.post(..., json=test_data)` serializes the transmitted JSON independently. Its generated signature is therefore neither provider evidence nor proof about the exact transmitted bytes. It may be cited only as source evidence about assumptions in Chapa's local tooling.

### `chapa webhook listen` — UNSUITABLE

The pinned implementation parses JSON and prints received payloads instead of preserving exact original bytes. It violates the M0.5-E raw-capture and non-logging boundary.

### CLI `tunnel` — NOT AN AUTHENTICITY SOURCE

The command invokes `pyngrok`; it only exposes a local service. It cannot make locally generated traffic or signatures provider-generated.

## 5. Test-payment safety decision

One manually completed payment is acceptable as a narrowly scoped M0.5-E exception only after separate E4 gates because current official documentation states that Test Mode uses no actual money, only Chapa-published test instruments, and continues sending webhooks. The exception is constrained to:

- confirmed TEST MODE only;
- exactly one fresh synthetic transaction and one payment completion;
- one Chapa-published test payment method/number selected at the payment gate;
- fictional reference data and the minimum hosted-initialization payload established by M0.5-C;
- no personal email, name, phone number, real customer, real payment credential, or live money;
- the sole purpose of producing one authentic provider webhook;
- no broad payment testing, second attempt after uncertainty, or live-mode parity claim.

This decision does not itself authorize checkout interaction. If any condition cannot be confirmed immediately before the relevant action, E4 remains blocked.

## 6. Public-exposure alternatives

The E2 receiver remains bound to `127.0.0.1`, `::1`, or `localhost`. E4 must not weaken that boundary; exposure must forward only the exact high-entropy public path to the exact loopback receiver.

1. **Existing maintainer-controlled HTTPS forwarding infrastructure — preferred.** It is eligible only after the maintainer identifies it and confirms TLS termination, body/header visibility, logs, retention, routing, access control, shutdown, and revocation. No such endpoint was supplied during E3.
2. **Ephemeral ngrok HTTPS endpoint — conditional fallback.** The local `ngrok` command is not installed. Standard ngrok HTTPS endpoints terminate TLS at ngrok's cloud service and re-encrypt traffic to the agent, so ngrok infrastructure can access body and headers; there is no end-to-end confidentiality from Chapa to localhost. Cloud Traffic Inspector stores metadata by default. Opt-in Full Capture stores headers/bodies and permits replay, with documented retention of 24 hours for Free and 72 hours for Hobbyist/Pay-as-you-go accounts. The local agent inspection database defaults to an allocation interpreted as 50 MB and can be disabled with `inspect_db_size: -1`; agent logging can be disabled. A fallback approval must require cloud Full Capture off, local inspection off, agent logs off, no replay, a fresh ephemeral URL, forwarding only to `127.0.0.1:<reviewed-port>`, immediate shutdown/revocation, and review of the account's current retention settings. This is safe enough only because all transaction data and the webhook secret are ephemeral and synthetic; it is not private from ngrok.
3. **Other tunnel provider — not selected.** Consider only if it offers a documented security/privacy advantage and receives separate review.
4. **webhook.site — reject as default.** The third party directly receives and stores the webhook payload and provider signatures instead of forwarding only to the controlled raw-capture boundary.

## 7. One-time webhook secret strategy

Immediately before an authorized E4 dashboard gate, the maintainer must create a new cryptographically random, high-entropy `webhookConfiguredSecret` solely for M0.5-E. It must be deliberately unequal to `apiSecretKey`, supplied and retained locally only, never printed or committed, and reported only as PRESENT/MISSING. It must be configured only for the Test Mode webhook and removed or replaced during immediate cleanup. Controlled inequality allows E5 to distinguish X1/C1 from X2/C2 rather than relying on coincidentally equal keys.

No secret was generated, read, or configured during E3.

- Stop the receiver and retain raw evidence locally only. Print no raw body, signature, digest, identifier, or secret.
