## 4. Authority and Evidence Precedence

Authority follows repository policy:

1. `docs/specification/TECHNICAL_SPECIFICATION.md` is normative until changed through approved change control.
2. Verified provider evidence and explicit maintainer adjudications.
3. Accepted ADRs.
4. Repository governance.
5. Approved implementation plans.
6. Source code and tests.
7. External recommendations.

Within the research record, a sanitized provider observation supports only its exact reviewed claim. An adjudication controls its classification; a plan records authorization and intended method but is not evidence that execution occurred. Documentation and provider observations remain distinguishable. Disposable harness code and local tests establish provenance and safety properties only, not Chapa behavior.

If evidence supports a specification change, F records a proposal rather than silently treating the specification as changed. Any material contradiction invokes Section 20.

## 6. Evidence-State Semantics

- **V**: a claim explicitly promoted by a maintainer/reviewer in an existing adjudication, or later explicitly promoted at the F5 gate. F automation may identify eligibility but cannot assign V.
- **D**: an unambiguous official-documentation claim that the master plan does not require provider verification to freeze. Documentation source and review date remain attached.
- **candidate-V**: a narrow, reproducible provider observation from a completed sub-milestone that awaits explicit maintainer promotion. It is never silently treated as V.
- **U**: insufficient, ambiguous, unavailable, contradictory, or deliberately deferred evidence.

Rules:

- Existing V findings remain V unless a material contradiction is escalated; they are not downgraded by consolidation.
- Existing U findings remain U unless F5 explicitly adjudicates sufficient evidence already in the repository.
- Test Mode does not prove live-mode parity.
- One response does not establish universal provider behavior.
- English messages and HTTP status alone are not stable payment-state or error discriminators.
- Local encoder, request-boundary, receiver, and cryptographic test behavior is local evidence only.
- Negative candidate matches reject only the exact tested construction and observation.

## 9. Manifest Strategy

### Canonical path and format

The proposed canonical manifest is `test/fixtures/chapa/manifest.json`, encoded as UTF-8 JSON with a top-level schema version and deterministically ordered `entries` array. Entry IDs are stable, lower-kebab-case identifiers; paths are repository-relative POSIX-style paths. Serialization is two-space-indented with one trailing newline.

### Existing contract fit

The three B JSON fixtures become initial entries using the Appendix F fields: operation, case name, Test Mode environment, captured date, method/path/status, evidence state V, sanitized flag, `fixturePath`, narrowly enumerated `supports`, and explicit `unresolved` claims.

The Appendix F contract requires `fixturePath` and is framed as a fixture manifest. It cannot cleanly describe C/D/E Markdown adjudications/observations or E's synthetic-vector test without pretending those artifacts are raw response fixtures. F2 must therefore present a minimal extension for maintainer approval before adding non-fixture entries:

```ts
type EvidenceArtifactKind =
  | 'sanitized-fixture'
  | 'sanitized-observation'
  | 'adjudication'
  | 'synthetic-vector';

interface ContractEvidenceManifestEntry {
  // Existing Appendix F claim, operation, environment, method/path/status,
  // evidence, sanitized, supports, and unresolved fields remain.
  artifactKind: EvidenceArtifactKind;
  artifactPath: string;
  humanReview: {
    status: 'approved';
    reviewedAt: string;
    adjudicationPath?: string;
  };
}
```

The proposal replaces the misleading `fixturePath` with `artifactPath`; it does not rename existing B files or change their evidence state. If changing Appendix F requires specification change control, F2 will keep the B-only manifest schema valid and record non-fixture C/D/E artifacts in the contract-freeze proposal until F6 explicitly approves the extension.

Every entry is claim-level and narrow. `supports` contains stable claim IDs defined in the matrix; `unresolved` names excluded generalizations. D / V / U is explicit; candidate-V remains representable as `candidate-V` only in the proposed extension and cannot be serialized as V. Human review records reviewer approval state and adjudication path, never an invented approval. A validator will verify file existence, schema, unique IDs, path containment, state consistency, and referential integrity, but existence or validation success never proves a claim. Maintainer comparison of `supports` against the referenced artifact is mandatory.

## 10. Contract Evidence-Matrix Design

The authoritative matrix will live in `docs/contracts/2026-08-25-m0.5-contract-freeze-proposal.md`. Each atomic claim row will contain:

- stable claim ID and operation/resource;
- exact claim and safety criticality;
- documentation source and provider-evidence source separately;
- current evidence state and adjudication authority;
- Test Mode/single-scenario boundaries;
- specification requirement or public type affected;
- category A, B, C, or D:
  - **A - Already consistent**: current normative behavior has sufficient D/V support;
  - **B - Evidence-supported specification delta**: current placeholder/ambiguity has sufficient evidence for a precise proposed change;
  - **C - Safe SDK policy despite provider U**: conservative public behavior proposed without misrepresenting provider support;
  - **D - Blocked/deferred**: unsafe to freeze from current evidence;
- candidate freeze wording, unresolved risks, raw-preservation requirement, and maintainer decision.

Rows will be atomic enough that one observed response cannot promote unrelated fields. Conflicting sources receive separate rows and trigger escalation rather than precedence by convenience.

## 12. Normalization Freeze Methodology

For every normalized field, F4 will record: provider/documentation source, evidence state, source wire field or fields, proposed public SDK field, transformation, safety justification, missing/unknown behavior, and whether exact raw preservation is required.

The review covers:

- **Payments**: initialization checkout URL/reference, verification status and identifiers, decimal money, dates, mode/payment method, and cancellation result without inventing a state transition.
- **Metadata**: bank identifiers/codes/lengths and integer/null flag fields without boolean coercion; currency parallel arrays with mismatch/missing-element behavior.
- **Refunds**: creation and verification remain blocked unless every target identifier and result field is supported; local form encoding cannot establish provider normalization.
- **Webhooks**: verified header, X1/C1 construction, both-header conflict behavior, event discrimination, exact raw bytes, and preservation of unknown event/status/payload fields.
- **References**: safe generation policy, 50-character observed boundary, conservative character grammar, uniqueness responsibility, and mapping among `tx_ref`, `trx_ref`, `reference`, `ref_id`, and `payment_reference` without assuming equivalence.

Required mismatch decisions include numeric/null bank flags versus boolean-looking fields, numeric/text parallel currency arrays versus object types, numeric verification amount versus decimal-string public money, endpoint-specific identifiers, link expiration versus cancellation state, and dual webhook signatures. Unknown enums remain accessible, unsafe coercion is prohibited, and `raw` is retained whenever normalized output loses provider detail or preserves future compatibility.

## 13. Specification-Delta Methodology

F4 will produce a dedicated section in the contract-freeze proposal containing proposed normative edits as requirement-level before/after intent, evidence links, classification, compatibility impact, and unresolved exclusions. It will not edit the specification.

Each proposal must be one of A/B/C/D from Section 10. Category B requires sufficient D/V evidence after F5. Category C must state that it is an intentional fail-safe SDK policy, not provider fact, and must be reviewed for compatibility. Likely review targets include currency and bank shapes, cancellation status promises, refund surface availability, `txRef` and money grammar, verification 404 handling, response `requestId`, and webhook algorithm/conflict behavior.

F6 may apply only the exact maintainer-approved delta set in a separate commit/checkpoint. Rejected, ambiguous, or evidence-dependent edits remain in the deferred register. An ADR may explain an approved revision but cannot authorize it.

## 14. Deferred-Contract Policy

Every U or partially resolved claim will be entered in the deferred-contract register within the contract-freeze proposal with owner milestone, affected public operation/field, safety consequence, required future evidence, permitted conservative behavior, forbidden inference, and reopening gate.

M0.5 may close with deferrals only when the corresponding version 1 operation or field is disabled, omitted, fail-closed, or explicitly constrained so production code cannot silently assume the missing contract. Refund provider behavior, duplicate-reference discrimination, universal cancellation state, webhook conflict semantics, and live parity are expected deferrals unless F5 finds sufficient already-committed authority. A new probe is not the default resolution path.

## 18. Raw-Evidence Retention/Deletion Policy Through Closeout

- Ignored raw captures remain local, untracked, unread during F, and outside Git.
- F relies only on committed sanitized artifacts and their adjudications; it does not re-open raw captures to strengthen a claim.
- `git ls-files research/contract-probes/.raw` must remain empty at every checkpoint.
- Manifest entries never point to `.raw/**` and never include raw hashes, signatures, bodies, or identifiers.
- Existing local raw data is neither deleted nor retained by automation during F. The maintainer owns retention through F5 in case an authorized human audit is required.
- At F7, the closeout records a maintainer decision to securely delete local raw captures or retain them for a named, time-bounded audit purpose. The decision records category, owner, deadline, and confirmation only—never contents or secret-derived values.
- Raw deletion is a separate explicit maintainer action; it is not inferred from F approval.
