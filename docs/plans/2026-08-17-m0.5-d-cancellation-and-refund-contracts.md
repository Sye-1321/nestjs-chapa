# Implementation Plan: M0.5-D Cancellation and Refund Contracts

**Status**: Approved
**Owner**: Sye (Sye-1321)

## 1. Goal

M0.5-D safely establishes bounded Chapa Test Mode evidence for cancellation and, only if its safety prerequisites can be resolved, refund creation and verification. It investigates OQ-02, the refund-reference portion of OQ-04, and OQ-11 without guessing identifiers, manufacturing payment state, replaying uncertain mutations, or implementing the production SDK.

## 3. Scope

### Included

- Cancellation success for one freshly initialized transaction, verification afterward, one already-cancelled attempt, and one unknown-reference cancellation.
- Paid/non-cancellable cancellation only if such a state is naturally and safely available.
- Refund prerequisite safety and refund-target identifier adjudication.
- Shared local boundary work, form-encoding foundation, and refund-specific encoding/builders/tests.
- Refund provider evidence only if D5 is explicitly approved.
- Scenario-specific D / candidate-V / U evidence adjudication.

### Excluded

- Reopening or altering M0.5-C; webhooks; broad amount, cancellation-body, or identifier trial-and-error research.
- Checkout automation or interaction, manufactured payment state, payment completion, real money, or real customer/payment data.
- Live-mode probes or claims of Test Mode/live-mode parity.
- Production `src/**`, `package.json`, dependencies, M1 work, the technical specification, or the M0.5 master plan.

## 4. Documented Candidates, Not Yet Verified

- Cancellation: `PUT /v1/transaction/cancel/{tx_ref}`, Bearer authentication, and **no request body**.
- Refund creation: documented path `POST /v1/refund/{tx_ref}`, Bearer authentication, and `application/x-www-form-urlencoded`; documented optional fields include `reason`, `amount`, `meta`, and `reference`.
- Refund verification: `GET /v1/refund/{ref_id}/verify`, Bearer authentication, no body.

These are documented candidates, not V-state claims. Current official documentation must be reviewed immediately before provider execution. The refund path placeholder does not establish which real identifier the endpoint accepts.

## 5. Global Safety and Evidence Requirements

- Chapa TEST MODE and fictional/synthetic data only; no real customer/payment data.
- No checkout automation or interaction, manufactured payment state, real payment completion, or real money.
- Every provider request requires its own exact Human Authorization Gate. One authorization permits exactly one reviewed network attempt.
- Exactly one network attempt per probe invocation, exact `attemptCount = 1`, zero automatic mutation retries, manual redirects, and bounded timeout.
- Credential state is shown only as PRESENT/MISSING. The secret is never printed, persisted, captured, or committed.
- Mutation transport uncertainty means STOP: preserve the exact identifier and do not replay. A separately authorized safe read may be considered only when its endpoint and identifier are independently safe and supported. Transport uncertainty is not provider evidence.
- Raw evidence exists only under `research/contract-probes/.raw/**` and remains ignored, untracked, local, and never committed or pasted into review artifacts. Tests use temporary directories and never write into the real `.raw` namespace.
- Evidence states are only D, candidate-V, or U. Automation cannot promote candidate-V to V.
- Conclusions are scenario-specific. English error text alone is not a safety-critical discriminator. Test Mode does not prove live-mode parity.
- Package, `src/**`, specification, master-plan, and M0.5-C boundaries remain untouched.

## 6. Exact Minimal Cancellation Sequence

D3 is bounded to this core sequence, with separate exact authorization before every request:

1. **Exactly one fresh initialization prerequisite**
   - One Test Mode `POST /v1/transaction/initialize`, using fictional data and one new unique reviewed `tx_ref`.
   - This is a D3 prerequisite, not a reopening of M0.5-C or covered by earlier authorization.
   - If transport-uncertain, preserve the `tx_ref`, STOP, and do not replay or proceed.
2. **Exactly one valid cancellation**
   - One `PUT /v1/transaction/cancel/{tx_ref}` for that fresh transaction.
   - Send exactly the documented **no-body** form. Do not send speculative JSON, form, empty-object, or alternate bodies.
   - If no-body unexpectedly fails, or current official documentation/provider evidence indicates a body is required, STOP and escalate. Do not send a speculative body afterward.
   - If transport-uncertain, preserve the `tx_ref`, STOP, and do not replay.
3. **Exactly one post-cancellation verification**
   - One separately authorized `GET /v1/transaction/verify/{tx_ref}` using the same exact `tx_ref`.
4. **Exactly one already-cancelled attempt**
   - One deliberate second `PUT /v1/transaction/cancel/{tx_ref}` using the same already-cancelled reference, again with no body.
   - This is the only repeat cancellation. There is **no third cancellation attempt**.
   - If transport-uncertain, STOP and do not replay.
5. **Exactly one unknown-reference cancellation**
   - One no-body `PUT /v1/transaction/cancel/{unknown_tx_ref}` using a reviewed, never-used, provider-valid-style synthetic reference based on already-observed accepted style.
   - It requires **no initialization prerequisite**.
   - If syntactically rejected, retain only that exact observation; do not try another reference or generalize unknown-reference semantics.

The core has exactly five provider requests: one initialization, two cancellations on its `tx_ref`, one verification of it, and one unknown-reference cancellation.

Paid/non-cancellable behavior is outside the core and may be investigated only if an eligible state is naturally and safely available. Do not open checkout, manufacture payment state, complete payment, or use real money. If unavailable, retain U. Any such request requires its own exact authorization and an approved plan update if it changes the agreed execution set.

## 7. Cancellation Boundary and Failure Rules

- Couple `PUT` only to the exact cancellation path and enforce bodyless cancellation.
- Reject any cancellation body, retry control, wrong host/origin/port/userinfo/method/path/query/fragment/header before fetch.
- Cancellation executes once, never retries, and never follows a redirect automatically.
- Successful HTTP transport does not itself establish cancellation state; review the response and separate verification observation.
- Do not extend conclusions beyond the exact tested state and reference style.

## 8. D5 Hard Gate: Refund Prerequisite and Target Identifier

Before **any** refund POST can be authorized, D5 must resolve both prerequisites.

### 8.1 Safe refundable state

Determine whether a refundable Test Mode transaction is naturally and safely available without checkout interaction or automation, manufactured payment state, payment completion, real money, or real customer/payment data.

If not available: authorize no refund POST, retain provider refund mutation behavior as U, continue only local OQ-11 work in D6, and allow M0.5-D to close with the item U.

### 8.2 Refund-target identifier hard gate

Determine whether the endpoint actually expects:

- merchant-supplied initialization `tx_ref`;
- provider-generated payment reference;
- `ref_id`; or
- another provider-defined identifier.

Do not infer this from `{tx_ref}` in the documented path. Do not guess, substitute candidates, or use trial-and-error mutations. Resolution must come from sufficiently clear current official Chapa documentation or safe already-observed provider evidence.

If it remains ambiguous: authorize **no refund POST**, perform no trial-and-error mutation, retain provider refund mutation behavior as U, allow local OQ-11 work to continue, and allow M0.5-D to close with the item U.

D5 approval must record the safe eligible transaction, exact resolved identifier kind and reviewed value, supporting official documentation or existing evidence, and the safe-refundable rationale. D7 remains blocked until the maintainer explicitly approves that record.

If later refund creation succeeds and returns a refund `ref_id`, refund verification may use only that exact reviewed returned identifier in a separately authorized `GET /v1/refund/{ref_id}/verify`. Never construct, guess, or substitute it.

## 9. Refund Provider Evidence Boundary

D7 is the only refund-provider execution checkpoint and requires explicit D5 approval plus passing D6 local verification. Every exact request still needs separate authorization.

Potential full, partial, invalid-amount, duplicate-reference, reference-boundary, reason, or meta scenarios are not automatically authorized. Select only a bounded reviewed set supported by the safe prerequisite and provider semantics, without unsafe repeated mutations. No broad grammar search is permitted; unsafe or unavailable scenarios remain U. Mutation uncertainty means STOP and no further refund POST.

## 10. Human Authorization Gate

Before every provider request display only:

- Operation ID; environment: TEST MODE; HTTP method; exact URL.
- Sanitized exact body or `no body`.
- Exact relevant `tx_ref`, refund target identifier, refund `reference`, or `ref_id`.
- Timeout; expected `attemptCount`: 1; automatic retries: 0; redirect behavior: manual.
- Credential state: PRESENT/MISSING.

Require exact `AUTHORIZE`. One authorization equals one request; no buffered, batch, or inherited authorization.
