# Implementation Plan: M0.5-E Webhook Evidence and Cryptographic Vectors

**Status**: Approved
**Owner**: Sye (Sye-1321)

## 1. Goal

M0.5-E will determine, within a strictly bounded Chapa Test Mode research process, which webhook signature contracts can be reproduced from exact original request bytes and which event shapes are actually observed. It will produce sanitized evidence and reproducible synthetic cryptographic vectors without exposing secrets, raw provider payloads, signatures tied to real secrets, or production infrastructure.

The work must distinguish official documentation claims from provider evidence and local-only safety proofs. Automation may classify claims only as D, candidate-V, or U; only the maintainer/reviewer may promote candidate-V to V.

## 3. Current Official Documentation Findings

Reviewed on 2026-08-25. These are documentation observations (D), not provider evidence:

### 3.1 Webhooks

Source: <https://developer.chapa.co/integrations/webhooks>

- A webhook is configured in the Chapa dashboard with a webhook URL and a “secret hash.”
- Chapa sends a POST containing a JSON event.
- `x-chapa-signature` is described as HMAC-SHA256 of the event payload using a secret key.
- `chapa-signature` is described as HMAC-SHA256 of a secret key signed using the secret key itself.
- The page uses “secret hash,” “secret key,” and webhook-secret language without proving their relationship to the API secret key.
- The JavaScript example hashes `JSON.stringify(req.body)`. It does not prove that the provider signs a parsed-and-reserialized representation or preserve original bytes.
- The prose says either signature may be sufficient when both are present, while also saying a missing or invalid header requires rejection. This is not a sufficiently clear acceptance policy.
- Non-200 acknowledgment is documented to cause redelivery every ten minutes, up to ten attempts over a 72-hour period.
- Documentation examples include transaction/refund and other event classes; those shapes remain D unless actually captured.

### 3.2 Merchant security handbook

Source: <https://developer.chapa.co/chapa-merchant-handbook>

- The handbook separately discusses dashboard webhook secret-hash configuration and API secret keys.
- It repeats the secret-on-secret description for `Chapa-Signature` and payload-HMAC description for `x-chapa-signature`.
- Its example also hashes `JSON.stringify(req.body)` and uses inconsistent signature-header casing.
- It does not establish exact original-byte behavior, encoding, or secret identity.

### 3.3 Test Mode versus Live Mode

Source: <https://developer.chapa.co/integrations/test-mode-vs-live-mode>

- Test Mode uses no actual money.
- The documentation states that webhooks continue to be sent in Test Mode.
- Test Mode evidence does not establish live-mode parity.

### 3.4 Official CLI documentation

Source: <https://developer.chapa.co/developer-tools/cli>

- The page lists `chapa webhook listen`, `chapa webhook ping`, and `chapa webhook verifywebhook`.
- It does not establish whether a ping signature is generated locally, remotely by Chapa, or not generated.
- A locally generated CLI signature may be a local test vector but is not provider-contract evidence.
- CLI use, installation, authentication, and execution remain unauthorized in E1.

## 4. Explicit Ambiguities

- Whether either signature is computed over exact original body bytes.
- Whether `JSON.stringify(req.body)` is merely an unsafe example or reflects provider canonicalization.
- Whether the dashboard-configured webhook value is the HMAC key for one or both headers.
- Whether the API secret key participates in either signature.
- Whether the dashboard webhook value and API secret key are ever identical, related, or independent.
- Exact output encoding and syntax for each header.
- Exact construction of `chapa-signature`.
- Header presence, original casing, and whether both are sent for the same event.
- Safe acceptance semantics when both headers are present and one is invalid.
- Whether CLI ping/verify exercises a provider-signed path.
- Which Test Mode event can be triggered without real money, checkout completion, or real data.
- Delivery timing, duplicate behavior, and Test Mode/live-mode parity.

Each unresolved ambiguity remains U unless exact provider evidence or sufficiently clear official evidence resolves the specific claim.

## 5. Scope and Non-Scope

### Included

- Disposable Node-built-in local receiver and offline crypto-analysis tooling under `research/contract-probes/**`.
- Exact raw-byte capture of a strictly bounded provider webhook if later authorized.
- Minimal signature-header presence/syntax/casing observations.
- Bounded documented-candidate HMAC reproduction.
- Raw-versus-reserialized local comparison.
- Sanitized event-shape observations and secret-free synthetic vectors.
- Negative local vectors and D / candidate-V / U adjudication.

### Excluded

- Production `src/**`, package/dependency work, NestJS/Express/Fastify implementation, or public API freeze.
- Technical-specification or M0.5 master-plan edits.

- General-purpose public servers, reusable tunnel infrastructure, broad endpoint research, or brute-force cryptanalysis.

## 6. Secret Taxonomy

Research code, plans, gates, and evidence must keep these identities distinct:

### A. API secret key

- Neutral name: `apiSecretKey`.
- Environment source may be defined later; never assume it is the webhook key.
- Used for authenticated Chapa API/CLI operations only when a later checkpoint explicitly authorizes such use.

### B. Dashboard-configured webhook secret/hash

- Neutral name: `webhookConfiguredSecret`.
- User-configured dashboard value unless provider evidence proves otherwise.
- Stored and supplied independently from `apiSecretKey`.

No secret value, real signature, or digest derived from a real secret may appear in Git, stdout/stderr, captures intended for commit, evidence Markdown, PR text, logs, URLs, or exception messages. Gates report only PRESENT/MISSING for each distinct secret.

## 7. Raw Evidence Model

Raw provider evidence:

- is written only below `research/contract-probes/.raw/**`;
- is ignored, untracked, local, and never committed or pasted into review artifacts;
- preserves exact request body bytes before parsing;
- preserves only the two relevant signature header values, minimal header-name casing evidence if required, and optional content type;
- excludes Authorization, cookies, query strings, unrestricted headers, connection metadata, and unrelated values;
- uses exclusive-create semantics and never overwrites an existing capture;
- is not evidence merely because a file exists.

Tests use temporary directories and never touch the real `.raw` namespace. A raw capture is reviewed locally before any sanitized derivative is staged.

- Execute only an E3-approved TEST MODE trigger and receiver exposure.
- Use one human authorization per provider-triggering action; no batch authorization.

### E5 - Offline cryptographic reproduction

- Perform all candidate HMAC computations offline against exact captured bytes.
- Evaluate each header independently, using only the pre-approved finite matrix.
- Compare exact raw bytes and one parsed/reserialized local variant without changing the production raw-byte rule.
- No provider requests or new exposure.

### E6 - Sanitized synthetic vectors and event-shape evidence

- Create reproducible synthetic vectors only after an algorithm/message/key relationship has been supported.
- Create sanitized field-shape evidence for only actually observed provider events.

### E7 - Adjudication and closeout

- Classify each header, algorithm, key relationship, encoding, raw-byte rule, and event shape as D, candidate-V, or U.
- Keep `chapa-signature` unsupported/U unless independently reproduced.

### E8 - One coherent M0.5-E PR

- Prepare one coherent PR after closeout.
- No ordinary E step edits the specification, production source, package metadata, or closed M0.5 evidence.

## 9. E2 Local Receiver Boundary

The disposable receiver must:

- use Node HTTP and filesystem built-ins only;
- bind locally by default and perform zero network action on import;
- accept POST only at one generated high-entropy research path fixed for the acquisition session;
- reject all other methods and paths without capture;
- reject query strings and avoid persisting them;
- enforce an explicitly configured bounded body limit while streaming;
- preserve exact received bytes before any JSON parsing;
- never parse JSON during receipt/capture;
- retain only case-insensitively selected `x-chapa-signature` and `chapa-signature`, optional content type, and minimum header-name casing evidence;
- never retain unrestricted raw headers, Authorization, cookies, or unrelated metadata;
- never print raw bodies, signatures, secrets, or capture contents;
- use exclusive-create capture files under `.raw` and refuse collisions;
- return 200 only after the intended capture is durably written;
- distinguish no inbound delivery, intended delivery captured, rejected unsolicited/malformed request, local capture failure, body-limit failure, and receiver timeout;
- stop after the exact approved inbound count or timeout;
- close listeners and clean up exposure after completion;
- include no automatic provider trigger, retry, webhook verification API call, or reusable public-server mode.

Unsolicited traffic is never classified as provider evidence merely because it reaches the receiver.

## 10. E2 Cryptographic Analysis Boundary

Local analysis uses `node:crypto` only:

- HMAC-SHA256;
- exact captured `Buffer`/`Uint8Array` message bytes;
- UTF-8 bytes for candidate secret/message strings where documentation justifies them;
- strict signature syntax decoding before comparison;
- expected 32-byte SHA-256 digest length;
- equal-length guard followed by `crypto.timingSafeEqual()`;
- no candidate secret, real signature, real digest, or raw body logging;
- JSON parsing only after a signature verifies in verifier-flow tests.

Analysis reports only candidate identifier, match/no-match, syntax/length classification, and safe evidence notes.

## 11. Finite Cryptographic Candidate Matrix

The initial matrix is frozen before E5 and contains only documentation-justified candidates:

| Candidate | Header | HMAC key | Message bytes | Purpose |
|---|---|---|---|---|
| X1 | `x-chapa-signature` | `webhookConfiguredSecret` UTF-8 bytes | exact raw body bytes | Dashboard-secret payload-HMAC reading |
| X2 | `x-chapa-signature` | `apiSecretKey` UTF-8 bytes | exact raw body bytes | Ambiguous “secret key” payload-HMAC reading |
| C1 | `chapa-signature` | `webhookConfiguredSecret` UTF-8 bytes | `webhookConfiguredSecret` UTF-8 bytes | Documented secret-on-secret reading |
| C2 | `chapa-signature` | `apiSecretKey` UTF-8 bytes | `apiSecretKey` UTF-8 bytes | Ambiguous API-secret-on-itself reading |

Rules:

- Test X and C headers independently; a match for one proves nothing about the other.
- Do not add mixed-key/message combinations, canonical JSON, prefixes, salts, trimming, case changes, hashing layers, or other transformations without explicit maintainer review and a direct documentation/evidence basis.
- Determine encoding candidates from observed header character set/length and current documentation. Initially consider lowercase/uppercase hexadecimal only if 64 hex characters are observed; consider base64 only if its syntax/length supports that bounded candidate.
- Do not try arbitrary encodings.
- No match means U; it does not justify matrix expansion.
- Never infer that `webhookConfiguredSecret` equals `apiSecretKey` from coincidental configuration or a single digest match without independently controlled secret values.

## 12. Raw Bytes Versus Reserialized JSON

For one captured JSON webhook, E5 compares locally:

1. observed provider signature against HMAC candidates over exact original raw bytes;
2. observed provider signature against the same candidate key over bytes produced by parsing and one ordinary `JSON.stringify` reserialization.

The second comparison is diagnostic only: it determines whether transformation changes the candidate input for that exact capture. Reserialized JSON is prohibited as production verifier input by REQ-WH-01 regardless of outcome. Parse failure or byte equality is recorded without inventing canonicalization rules.

## 13. Header Semantics

Evidence must separately record:

- presence/absence of each recognized header;
- safely observed character class, character count, and bounded encoding candidate;
- minimal original header-name casing where observable;
- case-insensitive local lookup behavior;
- which independently reproduced header verified.

One casing observation is not a provider guarantee. Both-present behavior is recorded but does not freeze “either valid means accept.” Any acceptance policy must follow the specification plus independently reproduced evidence; contradictory documentation alone is insufficient.

## 14. E3 Acquisition Decision Gate

Preference order:

1. An official Chapa test/ping mechanism proven to create a genuinely provider-generated and provider-signed webhook.
2. A provider-generated Test Mode webhook from an already-safe synthetic mechanism requiring no live money, real data, or prohibited checkout completion.
3. Otherwise, provider acquisition and unavailable event classes remain U.

Before selecting CLI ping/verify:

- inspect current official source or authoritative documentation;
- determine whether payload and signature originate locally, remotely from Chapa, or not at all;
- record authentication, network, storage, and secret implications;
- treat locally generated CLI signatures only as local vectors.

E3 must present a concrete acquisition record for maintainer approval. If authenticity or safety cannot be established, E4 remains blocked.

## 15. Public Exposure and Tunnel Gate

No public exposure is authorized by E1 or E2. If E3 determines it is necessary, the approval record must evaluate:

- whether a third party can see or retain raw payloads/signatures;
- secret exposure and logging behavior;
- one high-entropy route and inbound spoofing risk;
- one-shot receiver/body-limit/timeout behavior;
- provider URL acceptance and Test Mode reachability;
- process shutdown, URL removal, dashboard cleanup, and tunnel revocation;
- local firewall/listener scope and certificate termination;
- data-processing and retention implications.

Do not default to webhook.site because it discloses raw payload/signatures to a third party. Do not default to ngrok, Cloudflare Tunnel, or any other service. No tunnel command or dashboard change occurs before separate E3 approval.

## 16. Human Authorization Model and Inbound Accounting

Before each provider-triggering action, display only:

- operation/acquisition ID;
- environment: TEST MODE;
- exact configured webhook URL and high-entropy path;
- `webhookConfiguredSecret`: PRESENT/MISSING;
- `apiSecretKey`: PRESENT/MISSING if relevant;
- exact provider-triggering action;
- expected inbound delivery count;
- receiver timeout and body-size limit;
- acknowledgment policy (`200 after safe intended capture`);
- raw capture destination namespace;
- retry/redelivery risk;
- exposure and dashboard cleanup action.

Require exact `AUTHORIZE`. One authorization covers one provider-triggering action, not later actions.

Accounting distinguishes:

- provider-triggering actions initiated by the maintainer;
- inbound HTTP deliveries resulting from that action;
- duplicate/redelivery count;
- rejected unsolicited/malformed inbound requests;
- local-only crypto operations.

An inbound redelivery is not automatically a new provider-triggering action, but every delivery is counted. The receiver should acknowledge the intended event with 200 after safe capture to avoid intentionally creating a retry storm. Unexpected duplicates are captured only within the approved bound or cause stop/escalation.

## 17. Sanitization Policy

Committed evidence may retain only:

- acquisition ID, Test Mode, capture date, safe trigger classification;
- header presence, normalized header name, safe character class/length, and match classification;
- exact body length/hash only if the value is safe and cannot expose a real signature/secret relationship;
- sanitized field names, types, nesting, safe event/status names, and candidate conclusions;
- attempt/action/delivery accounting and unresolved notes.

Remove or replace names, emails, phone/account data, provider/customer identifiers, URLs/tokens, raw bytes, real signatures, real digests, and all secrets. Human sanitization review is mandatory before staging.

## 18. Synthetic Vector Policy

After provider reproduction supports an algorithm/message/key/encoding tuple, create committed vectors using:

- a clearly synthetic secret unrelated to either real secret;
- an exact sanitized/synthetic raw byte sequence;
- a locally generated expected digest using the supported tuple;
- explicit byte encoding and expected digest encoding;
- a note distinguishing the synthetic payload shape from provider-observed shapes.

The real provider signature and configured secrets are never committed. Synthetic vectors must be fully reproducible using Node built-ins and contain no provider/customer identifiers.

## 19. Event-Shape Policy

- Official examples such as `charge.success`, `charge.refunded`, reversed, failed/cancelled, payout, and refund categories remain D.
- A captured provider event may support candidate-V only for its exact observed event name, fields, types, nesting, and safe state values.
- Sanitization must preserve evidence structure without pretending replacement values were provider-observed.
- Uncaptured event classes remain D or U according to evidence quality.
- Unknown event names/statuses must remain preservable; no closed enum is inferred from examples.
- One event cannot prove ordering, duplicate, delay, or live-mode behavior.

## 20. Negative Local Vector Matrix

E2/E6 tests must include:

- valid exact raw bytes;
- one-byte payload mutation;
- whitespace/reformat mutation;
- missing recognized headers;
- malformed/non-decodable signature;
- wrong digest length;
- wrong secret and wrong payload;
- uppercase/lowercase request header-name lookup;
- signature value case behavior appropriate to the decoded encoding;
- both headers only when each relevant algorithm is independently reproducible;
- invalid-one/valid-other only after an acceptance policy is adjudicated;
- JSON parsing occurs only after successful verification;
- equal-length guard before `timingSafeEqual`;
- no secrets, signatures, digests, or raw body in errors/logs;
- import/startup causes zero network or public listener exposure;
- receiver method/path/body-size/timeout/collision/one-shot controls;
- tests write only to temporary directories, never real `.raw`.

Local negative vectors are safety tests, not provider evidence.

## 21. Stop Conditions

STOP for:

- any live-mode state, real money, real customer data, or required checkout/payment completion not explicitly approved;
- ambiguous secret identity, secret leakage risk, or pressure to make both secrets equal;
- raw body/signature/header output to terminal or unrestricted capture;
- tracked raw evidence or tests touching real `.raw`;
- receiver path/method/body limit not fixed, capture overwrite, or reusable public-server behavior;
- public exposure, dashboard change, CLI command, tunnel, or provider trigger without its explicit gate;
- acquisition authenticity that cannot distinguish local from provider-generated signatures;
- inbound count exceeding the approved bound, non-200 behavior likely to cause retries, or unexpected redelivery storm;
- broad encoding/secret/transformation brute force;
- need for dependency installation, `package.json`, `src/**`, specification, master-plan, or closed-batch changes;
- documentation/provider/specification conflict requiring normative change;
- unsafe sanitization or evidence that cannot support the proposed claim;
- rate limiting, blocking, unexpected provider action, or inability to clean up exposure.
