# Implementation Plan: M0.5 Chapa Provider Contract Verification

**Status**: Approved
**Owner**: Sye (Sye-1321)

## Goal

M0.5 gathers controlled Chapa test-mode evidence so that each version 1.0 safety-critical Chapa-dependent contract claim can be adjudicated by the maintainer/reviewer as:
- V - sandbox/test-mode verified;
- remaining D where documentation is unambiguous and verification is not required for the claim under the specification; or
- U / explicitly deferred when evidence is insufficient.

The automated implementation/probe agent records observations and may summarize them. It MUST NOT independently promote any contract to V. Final evidence-state adjudication belongs to the maintainer/reviewer.

## Scope

- M0.5 records evidence separately.
- M0.5-F may produce proposed evidence-matrix/open-question/specification changes.
- TECHNICAL_SPECIFICATION.md remains unchanged during ordinary probe batches.
- Any normative specification edit requires a separate maintainer-approved specification-change step.
- No automated agent may silently update the specification to match provider observations.

## Non-Goals

- no production SDK source;
- no src/**;
- no package.json merely for M0.5;
- no M1 CI/build/package work;
- no live-mode probes;
- no real customer/payment data;
- no normative TECHNICAL_SPECIFICATION.md edits during ordinary M0.5 batches;
- no public API/package implementation;
- no automatic evidence promotion;
- no automatic mutation retries;
- no attempt to prove live-mode parity from test mode.

## Raw vs Sanitized Evidence Model

### A. LOCAL RAW CAPTURES

- never committed;
- gitignored before first probe;
- may contain provider-generated operational evidence;
- authorization secrets should never be captured at all where avoidable;
- never paste raw captures into PRs;
- never paste raw captures into agent handoffs;
- never transmit them as review artifacts;
- ephemeral research evidence only.

### B. SANITIZED COMMITTED FIXTURES

May preserve:
- method;
- sanitized path;
- status;
- allowlisted headers;
- exact sanitized body structure;
- field names/types/nesting;
- safe status values;
- environment;
- capture date;
- normalization claim;
- evidence state;
- unresolved notes.

Must remove/replace:
- Authorization values;
- API secrets;
- webhook secrets;
- provider signatures tied to real/test secrets;
- names;
- emails;
- phone numbers;
- real account identifiers;
- unnecessary provider-generated identifiers;
- real customer/payment data.

Require HUMAN SANITIZATION REVIEW before a fixture may be staged.

## Mutation Safety Rules

- Chapa test mode only;
- fictional identities;
- unique reference for every independent mutation;
- intentional txRef reuse only for duplicate-reference probe;
- zero automatic retry for initialize/cancel/refund;
- network uncertainty after mutation never proves failure;
- uncertain initialize -> preserve txRef -> verify before any new initialize;
- refund/cancellation uncertainty -> no blind repeat;
- no generic retry middleware in probe scripts;
- bounded timeout;
- exact attempt count recorded;
- no secret in stdout/stderr.

For research probes:
- every probe invocation performs exactly one network attempt;
- no automatic retries for reads or mutations;
- a second read observation is a separate deliberate invocation;
- mutation uncertainty is never blindly replayed.

This does NOT change the future SDK safe-read retry policy.

## D/V/U Adjudication Rules

**D**: Official docs support the specific claim, but ambiguous provider behavior has not been fixture-verified.
**V**: A sanitized reproducible test-mode observation directly supports the specific claim.
**U**: Evidence remains missing, contradictory, unstable, unavailable, or unsafe to infer.

A safety-critical provider-dependent claim that the specification requires M0.5 to verify cannot remain merely D at M0.5 exit.

It must either:
- have enough evidence for maintainer-adjudicated V state; or
- be explicitly deferred from the shipped contract.

D may remain only for documented non-safety-critical claims where the specification does not require fixture verification.

Rules:
- evidence is claim/field/scenario specific;
- one V fixture does not make an entire endpoint V;
- unknown/inconsistent behavior stays U;
- human-readable English-message matching alone cannot establish a safety-critical provider error discriminator;
- test-mode V does not prove live-mode parity;
- maintainer/reviewer performs final adjudication.

## Risks / Open Questions

- inability to reproduce provider state
- provider rate limiting/blocking
- webhook delivery reachability
- contradictory docs vs observations
- sanitization destroying evidence
- test/live parity limits
- unsafe or impractical boundary probing

Unresolved risks lead to escalation or explicit deferral, never guessed behavior.

## Definition of Done

- every shipped safety-critical Chapa-dependent claim is V or explicitly deferred;
- fixture manifest complete;
- committed fixtures sanitized and human-reviewed;
- relevant OQs resolved or explicitly deferred;
- evidence-state adjudication completed by maintainer/reviewer;
- proposed specification/contract changes are separately reviewable;
- no production payment code exists.

M0.5 completion does NOT imply:
- M1 complete;
- SDK implemented;
- live-mode parity proven;
- all Chapa endpoints supported.
