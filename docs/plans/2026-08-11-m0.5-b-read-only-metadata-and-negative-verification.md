# Implementation Plan: M0.5-B Read-Only Metadata and Negative Verification

**Status**: Approved
**Owner**: Sye (Sye-1321)

## 1. Goal
The goal of M0.5-B is to establish provider execution behavior for read-only endpoints without mutation side-effects. This batch will safely test `GET /v1/banks`, `GET /v1/currency_supported`, verify an unknown transaction, and observe safe response headers, building upon the local-only M0.5-A harness.

## 2. Scope
This plan covers ONLY:
- B1: `GET /v1/banks`
- B2: `GET /v1/currency_supported`
- B3: `GET /v1/transaction/verify/{synthetic unknown reference}`
- B4: safe response-header / request-correlation-ID observation using the above read-only requests where possible.
- No mutation is allowed.
- All provider observations in M0.5-B are Chapa test-mode only and do not establish live-mode parity.

## 3. Non-Goals
Explicitly excluded from this batch:
- initialization;
- duplicate txRef;
- amount-boundary probing;
- cancellation;
- refunds;
- webhooks;
- live-mode testing;
- SDK production implementation;
- specification edits.

## 4. Authority / Traceability
- `docs/specification/TECHNICAL_SPECIFICATION.md` remains the normative authority.
- The approved M0.5 master plan (`docs/plans/2026-08-08-m0.5-contract-verification.md`) is the governing execution plan.
- Traces back to REQ-TEST-01, REQ-TEST-02, REQ-TEST-03, REQ-NET-12, REQ-ERR-01, OQ-05, OQ-06, OQ-09, ADR-016.

## 5. Current State

- Existing M0.5-A harness tests pass 51/51.
- M0.5-B implementation has NOT started.
- No provider evidence exists.
- Production SDK work remains blocked by M0.5.

## 7. Approved Provider Operations
- `GET /v1/banks`
- `GET /v1/currency_supported`
- `GET /v1/transaction/verify/{tx_ref}` (where tx_ref is a fictional, synthetic unknown reference)

## 8. Provider Execution Boundary
Provider access is constrained by:
- protocol exactly https:
- origin exactly https://api.chapa.co
- standard HTTPS port only
- GET only
- no userinfo
- no query
- no fragment
- pathname exactly within the approved M0.5-B allowlist.
Every research invocation performs exactly ONE network attempt. No automatic retry. A second observation is a separate deliberate invocation.

## 9. Credential / Secret Handling
- Provider credentials remain environment-only (`CHAPA_SECRET_KEY`).
- Do not place credentials in source, CLI arguments, URLs, logs, or evidence files.
- The exact authentication requirement for each M0.5-B endpoint must be verified before provider execution rather than guessed.

## 10. Raw Evidence Policy
- Transport timeout/failure is NOT provider contract evidence.
- Raw evidence remains local under `research/contract-probes/.raw/**` and must remain ignored/untracked.

## 11. Sanitized Evidence Policy
- Sanitized evidence is committed only after human sanitization review.
- Automation may record D, candidate-V, U.
- Only maintainer/reviewer may promote candidate-V to V.

## 12. Response-Header Discovery Policy
- B4 is primarily an observation objective, not automatically a separate provider request. B4 may be satisfied by the SAME raw capture and sanitized fixture produced by B1, B2, or B3.
- B4 does NOT automatically require a fourth network request, a duplicate raw artifact, or a duplicate sanitized fixture.
- A separate read-only request is permitted only if existing B1/B2/B3 observations are insufficient, the exact request is separately reviewed, and the Human Authorization Gate explicitly authorizes it.
- B4 (OQ-06) header discovery must never bulk-capture arbitrary header values.
- Allow safe allowlisted header values or unknown response-header names only.
- A specific unknown header value may be collected only after human review and explicit allowlisting.

## 13. Synthetic Unknown-Reference Strategy
- B3 must use a fictional, high-entropy synthetic unknown reference.
- The exact synthetic reference and exact URL must be reviewed before the request is authorized.
- Do not claim a reference grammar is provider-valid until authoritative documentation or M0.5 evidence supports it.
- An unknown-reference observation does NOT establish the unpaid/pending transaction discriminator required by OQ-09 / REQ-NET-12. Actual unpaid/pending lifecycle evidence remains for M0.5-C.

## 15. Checkpoint / Execution Phases
This project uses checkpoint commits.
- **Checkpoint 1:** approved M0.5-B plan only.
- **Checkpoint 2:** local-only harness adaptation + tests.
- **Human Authorization Gate:** before ANY provider request.
- Execute B1 first. Review B1 before B2. Review B2 before B3.
- B4 should reuse B1/B2/B3 evidence when sufficient and should not automatically cause a fourth request.
- The eventual M0.5-B work should remain ONE coherent pull request with multiple reviewed commits.
- Do NOT prescribe: plan PR -> implementation PR -> closeout PR.

## 16. Local Validation Requirements
The future local-only harness adaptation must prove at minimum:
- external/provider execution disabled by default;
- importing/building a probe performs zero network calls;
- exact HTTPS provider origin enforcement;
- wrong host/subdomain/suffix rejected before fetch;
- non-standard port rejected before fetch;
- userinfo rejected before fetch;
- query rejected before fetch;
- fragment rejected before fetch;
- non-GET methods rejected before fetch;
- mutation/unknown paths rejected before fetch;
- approved B1/B2/B3 paths accepted only in explicit provider mode using injected fake fetch;
- all rejected provider cases prove fake fetch invocation count = 0;
- accepted fake-provider request proves exactly one fetch invocation;
- redirect mode remains manual;
- no automatic retry;
- M0.5-A loopback behavior remains passing;
- Authorization/credential values are never persisted in capture metadata;
- B3 exact synthetic reference reviewed is the exact reference later used for URL construction/execution.

All of these tests remain local/fake/loopback only. They do NOT authorize provider execution.

## 17. Human Authorization Gate
- A human maintainer/reviewer MUST explicitly authorize the execution before any real provider request is made.
- The exact synthetic unknown reference and exact URL for B3 must be reviewed.

## 18. Provider Probe Procedure
- Before each endpoint's first provider invocation: review authoritative/current provider documentation for the endpoint's authentication requirement.
- Do not guess auth behavior.
- Only if authentication is confirmed required may the probe lazily read `CHAPA_SECRET_KEY` from the environment.
- Never put the secret in CLI args, URL, logs, raw evidence, or committed fixtures.
- Execute probe.
- Observe raw bytes generated in `.raw/`.
- Run sanitization.
- Review sanitized candidate.

## 19. Evidence Adjudication
- Automation may record D, candidate-V, or U.
- Only the maintainer/reviewer may promote candidate-V to V.
- Evidence may remain D or U where permitted by the approved M0.5 master plan.

## 20. Expected Repository Boundary
Expected modifications:
- `research/contract-probes/README.md`
- `research/contract-probes/probe.mjs`
- `research/contract-probes/lib/request.mjs`
- `research/contract-probes/test/harness.test.mjs`

If implementation demonstrates `capture.mjs`, `env.mjs`, or `sanitize.mjs` must change, STOP and record the discovery before expanding the boundary.
Do not pre-authorize evidence fixture filenames before observations exist.

## 21. Stop / Escalation Conditions
Immediate STOP/escalation for:
- arbitrary external network access required;
- more than one automatic request attempt;
- hidden retries;
- hidden redirects;
- secret might be logged or persisted;
- Authorization might enter raw capture;
- raw evidence becomes tracked;
- provider response cannot be safely sanitized;
- authentication remains unclear;
- reference syntax remains too uncertain for a meaningful B3;
- provider behavior conflicts with specification;
- rate limiting/blocking;
- dependency installation becomes necessary;
- `package.json` becomes necessary;
- `src/**` becomes necessary;
- technical specification edit appears necessary;
- scope drifts into M0.5-C or later.
