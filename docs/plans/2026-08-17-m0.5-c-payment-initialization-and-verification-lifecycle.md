# Implementation Plan: M0.5-C Payment Initialization and Verification Lifecycle

**Status**: Approved
**Owner**: Sye (Sye-1321)

## 1. Goal
The goal of M0.5-C is to establish provider execution behavior for the payment initialization and verification lifecycle. This plan safely gathers test-mode provider evidence for transaction creation, metadata limits, duplicated references, state verification, and safe local timeout behavior.

The plan must preserve the governing M0.5 safety model and must NOT claim provider behavior that has not been observed.

## 2. Scope
This plan requires gathering evidence for:
- valid initialization
- verification of a transaction created during M0.5-C
- unpaid/pending verification
- invalid initialization
- initialization identity-field requiredness
- amount grammar and bounded amount probes
- tx_ref format/length probes where safely testable
- duplicate tx_ref using exactly one deliberately reused provider-accepted reference
- provider-valid-style unknown-reference verification only after accepted-reference evidence exists
- failed-state verification only if naturally/reproducibly available
- uncertain initialization / timeout procedure
- evidence adjudication and closeout

## 3. Non-Goals
Explicitly excluded from this batch:
- cancellation
- refunds
- refund-reference research
- webhooks
- direct charges
- transfers
- checkout automation
- real payment completion
- real customer/payment data
- live-mode probes
- production SDK source
- src/**
- package/dependency work
- package.json changes
- M1 work
- routine TECHNICAL_SPECIFICATION.md edits

M0.5-D owns cancellation/refunds.
M0.5-E owns webhooks.

## 6. Human Authorization Gate
Before EVERY real provider request, the reviewer must see only:
- operation ID
- environment: Chapa TEST MODE
- HTTP method
- exact URL
- sanitized request body, if applicable
- exact tx_ref
- timeout
- expected attemptCount: 1
- automatic retries: 0
- credential status: PRESENT or MISSING

Never show the credential.
Authorization applies only to that exact request.
Authorization for one request does NOT authorize the next one.

## 7. Request Header / Secret Rules
For initialization, the future harness may allow only provider-reviewed required headers.

Expected after documentation re-review:
- Authorization
- Content-Type: application/json

Do not treat this wording as provider verification.
Reject arbitrary request headers.

The secret must never enter URL, request body, stdout, stderr, capture metadata, fixtures, or Git history.
Authorization remains header-only and must never be persisted.

## 8. Mutation Safety Requirements
- Chapa TEST MODE only
- fictional/synthetic identities only
- no real customer/payment data
- exactly one network attempt per probe invocation
- zero automatic retry for initialize
- every independent initialization gets a unique tx_ref
- reuse tx_ref ONLY for the deliberate duplicate-reference probe
- no hidden redirect follow-up
- bounded timeout
- attemptCount recorded
- network uncertainty after mutation does NOT prove failure
- uncertain initialize -> preserve exact tx_ref
- do NOT blindly replay POST
- separately verify preserved tx_ref
- no credentials in stdout/stderr/capture/Git
- probes must be performed and reviewed one at a time

## 12. Required Execution Order

1. **local-only harness mutation-boundary adaptation**
2. **Baseline valid initialization**:
   - exactly ONE POST
   - unique reviewed tx_ref
   - review response before proceeding
   - if outcome uncertain: STOP immediately
3. **Verify accepted transaction**:
   - exactly ONE GET using the exact accepted tx_ref
   - this observation may satisfy both created-transaction verification and OQ-09
   - do not automatically duplicate the GET
4. **Minimal identity-field probe**:
   - start with exactly one minimal initialization after baseline is understood
   - amount + currency + unique tx_ref
   - omit identity fields
   - only minimum targeted follow-ups if evidence specifically requires them
   - never enumerate every field permutation
5. **Invalid initialization**:
   - exactly one reviewed baseline invalid case first
   - prefer missing a required core field such as amount unless prior evidence suggests a more informative case
   - do not generalize all validation behavior from that observation
6. **Amount suite**:
   - every case is one separately reviewed POST
   - every independent case uses a unique tx_ref
   - exact amount string must be human-reviewed before request
   - no broad search for maximums
7. **tx_ref suite**:
   - bounded cases only
   - no brute-force grammar discovery
   - every independent mutation gets a new tx_ref
   - exact complete grammar/max remains U if not safely established
8. **Duplicate tx_ref**:
   - prerequisite is one already accepted tx_ref
   - perform exactly ONE second initialization with that exact accepted tx_ref
   - no third collision attempt
9. **Provider-valid-style unknown**:
   - only after accepted-reference evidence gives a meaningful form
   - review exact never-used reference AND exact verification URL
   - exactly ONE GET
   - if still syntactically rejected, do not force a general unknown-reference conclusion
10. **Failed state**:
    - only if naturally/reproducibly available without checkout/payment automation
    - otherwise explicitly retain U/defer
11. **local uncertain-initialization procedure verification**
12. **evidence adjudication and closeout**

## 14. Uncertain Initialization Protocol
If POST initialize produces timeout, connection reset, DNS/TLS/socket uncertainty, or any transport failure where Chapa may have received the mutation:

1. record attemptCount = 1
2. preserve the exact tx_ref
3. DO NOT replay POST
4. DO NOT substitute a fresh tx_ref to avoid understanding the first result
5. STOP and review
6. separately authorize GET verification of the preserved tx_ref
7. adjudicate only after that evidence

Transport uncertainty is not provider-contract evidence.
Do not intentionally manufacture a real provider timeout.
Prove the procedure primarily with fake/local harness tests.

## 15. Provider/Harness Boundary
M0.5-C adds only:
`POST /v1/transaction/initialize`

and uses:
`GET /v1/transaction/verify/{reviewed_reference}`

Do NOT remove/regress the existing M0.5-B harness support for banks, currencies, and verification.
Existing M0.5-A/B behavior must remain passing in regression tests.
However, M0.5-C does NOT authorize new B1/B2 provider requests merely because the harness retains those paths.

Method/path coupling for initialization must be exact.

POST initialize requirements:
- body required
- JSON body
- Content-Type application/json
- body forwarded once
- exactly one fetch
- manual redirect
- zero retry

Expected future code boundary:
- `research/contract-probes/README.md`
- `research/contract-probes/probe.mjs`
- `research/contract-probes/lib/request.mjs`
- `research/contract-probes/test/harness.test.mjs`

If implementation later needs changes to `capture.mjs`, `env.mjs`, `sanitize.mjs`, or a new helper, the plan must require STOP + review before expanding scope.

## Discoveries / Plan Updates

After multiple individually authorized M0.5-C requests, temporary per-request scripts became operationally cumbersome, so after an explicit STOP + review a local interactive runner was introduced.

The local interactive runner:
- preserves Human Authorization Gate per exact request
- has no provider batch mode
- preserves one-attempt/zero-retry mutation safety
- keeps raw captures local
- does not itself promote evidence to V
- does not expand M0.5-C provider endpoint scope
